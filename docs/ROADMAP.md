# 织影 Weave 产品与开发总规划

> **版本**：v1.1 定稿 · 2026-10-10 · 仓库 `/home/user/default_label`，只在 main 分支开发并直接推送。
> **来历**：在 v1.0 草稿的基础上，逐条处理了《完整性审查》（42 条）和《可行性审查》（19 条加 5 条轻微意见）。每条的处理结果见附录 J；没采纳或只部分采纳的，理由写在 §8.3。
> **执行方式**：开发由 Claude（AI 编码代理）一个人完成。Claude 接触不到的东西，包括你的 NAS、手机真机、朋友的算子和各种外部账号，全部单独标为"需你提供"或"需你验收"（见 §7）。
> **工作量单位**："会话"指 Claude 的一次集中开发，交付一个能单独验收的增量（含测试和文档）。平均每次净增约 150–400 行代码，其余时间花在调研、测试和返工上。到 v1.0 时，总代码量的目标是 4–5 万行，其中测试约占 40%。每个里程碑结束时统计一次，超出预算 30% 就先做精简，再继续开发新功能。

## 0. 一页摘要

### 0.1 织影是什么

织影是部署在你自己 NAS 上的 AI 影像创作工作室。

- 普通用户输入一句话就能出图、出视频，也可以一键套用热门效果模板。
- 长篇创作者可以把一个故事（或一个多集系列）从大纲、剧本、分镜一路做到关键帧、镜头视频、配音和成片。
- 算力来自可插拔的远端"算子"。现在用的是朋友的 5090，以后可以接更多机器，也可以接其他种类的算子（例如配音、超分）。
- 所有素材长期存放在你自己的硬盘上。

### 0.2 现状判断

单人创作的闭环已经能跑通，但要对外提供服务，还缺四块地基：

1. 多用户的安全与权限：没有角色、没有后台、没有限流。
2. 算子与凭证的界面化管理：现在只能改环境变量，token 只存在内存里。
3. 可靠、公平的调度：取消不生效，超时会重复提交，任何用户都能插队。
4. 数据与运维保障：没有备份、告警、缩略图，也没有测试。

另外，有一批现有缺陷会导致数据丢失、算力浪费或凭证外泄，必须最先修掉（§3.2）。

### 0.3 本版相对草稿的主要变化

## 2. 产品定位与业务

### 2.1 定位与价值

| 价值 | 含义 |
| --- | --- |
| 简单 | 首屏只有一个输入框、模式切换和生成按钮。预设、模板和高级参数逐层展开，新手不需要懂"步数""CFG"是什么 |
| 长周期 | 故事工坊、系列和资产库，撑得起几周到几个月的连载创作。素材能检索、能复用，也能追溯来源 |
| 可控 | 每次生成都记下完整配方（提示词、预设、参数、实际种子），可以复现、做变体、做对比。有候选和定稿，也有版本历史 |
| 自主 | 数据在你自己的 NAS 上，算子可以替换、可以扩展，不依赖任何一家 SaaS |

### 2.5 容量测算

> 以下数字都是**假设**，前提是视频和图片都在朋友那张 5090 上本地生成（待 §9.2 第 13 项确认）。如果视频其实是 ComfyUI 的 API 节点在调用 MiniMax 云端，那么会有三点变化：提示词和参考图会流向第三方 MiniMax；每次调用都有真金白银的成本；本节的容量测算和附录 B 的定价都不再成立，需要改为"按次成本"模式（模型目录里的 `cost` 字段已经为此预留）。

- 一张 GPU 每天约有 86,400 GPU 秒。
- 只出视频：每条 15–30 分钟，每天约 48–96 条。只出图：每张 30–40 秒，每天约 2,000–2,800 张。
- 一个 60 镜头、每镜 5 秒的故事：视频部分 60 × 15–30 分钟 = 15–30 小时，关键帧候选再加 2–3 小时，**合计约 17–33 GPU 小时，相当于整张卡跑 1–1.5 天**。
- 每用户每天默认最多 6 条视频。按这个上限，**8–16 个活跃用户就能把整张卡占满**。所以需要一个**全站每日容量护栏**：当天预计用量超过容量的 80% 时，新的视频任务自动转入闲时通道（SCH-03）。

由此得出几个必然的产品选择：

1. 两段式生产：先批量出关键帧（便宜），挑好、定稿后再出视频（昂贵）。
2. 闲时通道：批量视频默认放到夜间跑。
3. 按用户公平调度，防止一个人占满 GPU。
4. 价格挂在模型目录上。GPU 秒只用于换算容量，不直接作为价格。
5. 从根本上扩容，靠接入更多算子。

### 2.7 产品与设计原则

1. **入口简单，能力藏在里面。** 首屏只有一个输入框、模式切换和生成按钮。
2. **控件按算子能力显示。** 算子不支持的参数，界面上就不出现，不留"摆设"控件。
3. **每次生成都可复现。** 配方和实际种子写进资产，删掉任务也不会丢。
4. **内容是数据，不是代码。** 预设和模板在后台维护，仓库里自带一份种子数据。
5. **业务层和算子解耦。** 业务只依赖模型目录和能力声明；换算子或加算子时，业务层不用改。
6. **适配 NAS。** 单进程、单个 SQLite，不引入 Redis 或消息队列。本机 CPU 只做探测、截帧、缩略图、无损拼接这类轻活；GPU 的活全部交给远端算子。
7. **视觉语言。**
   - 不用任何渐变。落地页和登录页用"点阵背景 + 鼠标水波"，其余页面是简约、紧凑的大厂风格。
   - 只有一个强调色 `#4d8dff`，状态用 ok、warn、danger 三种颜色表示。
   - CI 里有一条规则：除了 `.dots-bg` 和 `.grid-lines` 这两个图案类以外，代码中出现 `gradient` 就判为失败。
8. **手机和桌面同样重要。**
   - 手机端只放 5 个一级入口：**创作**（包含流水和队列）、**灵感**（包含工作流）、**故事**、**资产**、**我的**。
   - 弹层统一用底部 Sheet；表格在手机上改为卡片显示。
9. **无障碍基线（PLT-29）。**
   - 图标按钮都有 `aria-label`，焦点清晰可见。
   - 正文对比度不低于 4.5:1。
   - `prefers-reduced-motion` 打开时关闭水波（现有 DotField 已经支持，会补上测试）。

### 4.5 跨领域统一决议

| 主题 | 决议 | 理由 |
| --- | --- | --- |
| 迁移 | 用 `schema_migrations` 表和 TS 迁移文件。执行前先 `VACUUM INTO` 备份，每个迁移一个事务。每个迁移声明自己是不是 `compat`。启动时检查"代码版本 ≥ 库里记录的 `min_code_version`"，不满足就拒绝启动并给出中文提示。迁移期间先开始监听端口，`/readyz` 返回 `503 {migrating:true, progress}` | 兼容迁移可以直接回滚镜像；健康检查和更新脚本不会把迁移中的状态误判为失败 |
| 大数据量变更 | 迁移里只做结构变更和小数据量转换。FTS 首次建索引、`gen` 回填、缩略图回填、故事拆表都交给 `jobs`（可续跑、可限速） | 避免启动卡住，也避免触发 OOM |
| 回滚 | **兼容迁移**：直接换回旧镜像。**不兼容迁移**：用旧镜像，再恢复迁移前的备份；脚本会提示"升级之后产生的数据会丢失"，并列出丢失的时间窗口 | 把语义写清楚 |
| 测试 | 单元和集成测试用 node:test 加假算子；E2E 用 Playwright，M0a 起只跑 Chromium 的两个视口，M4 加上 WebKit。测试名以工作项编号开头，例如 `OPR-04 …`，由 `scripts/trace.ts` 检查覆盖 | 少加依赖；可以追溯到工作项 |
| 运行时 | 使用 Node 22.22 原生的类型剥离，去掉 tsx，打开 `erasableSyntaxOnly` 检查 | 实测空闲内存从约 170 MB 降到约 105 MB |
| 主密钥 | 用 `WEAVE_MASTER_KEY`（或 `_FILE`）。没配置时，自动生成 `/data/keys/master.key`，并在后台持续警告。所有密钥都放进一张 `secrets` 表，用 AES-256-GCM 加密，密文带版本前缀，AAD 绑定密钥名。轮换 CLI 推迟到形态 B | 只有一处加密；以后可以轮换 |
| 密码哈希 | 用 Node 内置 scrypt，参数 N=2^15、r=8、p=1，**`maxmem` 设为 64 MiB**，用信号量限制最多同时 2 个哈希计算。旧的 bcrypt 哈希在用户登录成功后透明升级 | 没有原生依赖；默认的 maxmem 会直接报错；不加并发限制的话峰值约 128 MiB |
| 角色 | 三种：`user`、`staff`、`superadmin`，权限点写在代码里。非管理员访问 `/api/admin/*` 一律返回 **404** | 后台不向普通用户暴露任何数据（前端的后台分包仍然可以被下载，但里面不含数据） |
| 敏感操作 | "重新验证"：管理员开了 TOTP 就输入 TOTP，没开就输入密码。每次验证只对当前这一个操作有效，没有 15 分钟窗口，也不自动重放 | 比 sudo 模式简单 |
| 人机校验 | 形态 A 不做 PoW（邀请制本身就是闸门）；形态 B 开放注册时再做 | 避免 HTTP 环境下 `crypto.subtle` 不可用的问题 |
| 设置 | `app_settings` 加注册表，后台表单根据注册表自动生成；功能开关也放在这里。M1 之前先用环境变量做开关 | 只有一处配置来源 |
| 审计 | 一张 `audit_logs` 表，存中文摘要和打码后的 diff。哈希链推迟到形态 B | 成本低 |
| 媒体处理 | 镜像内置 ffmpeg 和 ffprobe，用于视频和缩略图。**上传的图片不重新编码**，用纯 JS 读文件头、剥离 EXIF；PNG 的 iTXt 标识也用纯 JS 写入。临时文件放在 `/media/.tmp`，不放 tmpfs | 不损失画质、不丢 GIF 动画、省 CPU；tmpfs 会占用容器的内存额度 |
| 缩略图位置 | `THUMB_DIR=/data/thumbs`（建议放在 SSD 上） | 浏览时不用唤醒机械盘 |
| 能力声明 | 只有一份 `CapabilitySpec`，前后端共用。M0a 先用静态 v0，M3 改为入库 | 一份契约 |
| 公平调度 | 加权公平排队，键值为"近 24 小时 GPU 秒 ÷ 套餐权重"；优先级只在同一用户自己的队列里生效；只有管理员能全局插队；另有全站每日容量护栏 | 防止一个人占满 GPU |
| ETA | 预计开始时间 ≈ 同类任务中排在前面的数量 × EWMA p50 ÷ 该类并发数，区间取 p50 到 p90 | 不再模拟整套派发过程，误差在可接受范围内 |
| 路由 | 先按优先级，熔断后故障转移；故事亲和只保留一条规则："同一故事上次成功的那台优先" | 两台机器的规模下，加权随机等策略用不上 |
| 计费 | M3 只定义钩子，在任务上挂 `hold_id`，钩子用空实现。M9 做精简账本。价格挂在模型目录上，`cost` 记录货币成本 | 兼容"按 GPU 时长"和"按次计费"两类算子 |
| 内容管理 | 预设、模板各有专表；后台共用 DataTable 和表单组件；协议文本先写成静态页面（形态 B 再改为带版本的 `pages` 表） | 简单 |
| 搜索 | FTS5 trigram，`detail=none`，查询用 LIKE；结果按时间排序；高亮在前端用子串匹配实现 | `detail=none` 不支持短语 MATCH，也不支持 bm25 和 snippet；这是有意的取舍 |
| 资产主键 | 不重建表。加 `seq INTEGER` 列和唯一索引，由应用分配，迁移时按 `(created_at, id)` 回填；FTS 用 contentless 表，`rowid = seq` | 避免整表复制 |
| 故事存储 | 分两步：M0a 先止血（`rev` 乐观锁、409 冲突、localStorage 重放，保留 keepalive，**不用 sendBeacon**）；M7a 拆表，改为 ops 增量保存，并且按需迁移 | sendBeacon 同样受 64 KB 限制，而且只能发 POST |
| 任务状态 | 对外的 `status` 不变，另加 `phase` 字段；`held` 状态只在形态 B 加 | 兼容现有前端 |
| 回调 | 默认轮询，算子支持时用批量查询；Webhook 默认关闭 | NAS 可能在 CGNAT 后面 |
| 算子配置来源 | 首次启动时从 env 导入一次，之后一律以数据库为准；env 和库里的值不一致时，日志和后台各提示一次 | 去掉"env 托管 / 界面托管"双模式 |
| 工作流 | 用代码定义的步骤数组，配一个通用执行引擎；后台只能启停和调整默认参数。JSON DSL、表达式引擎和用户自定义工作流推迟到 P2。"算子侧模板"留作另一种类型（D23） | 7 个官方工作流用不着一套 DSL |
| 告警通道 | 邮件、企业微信、Bark、通用 Webhook（可以配置 JSON 模板，覆盖飞书和钉钉） | 国内可达，实现量小 |
| 可观测性 | 一张 `error_events` 表加后台列表，再加 RSS、磁盘、队列的简单采样。`/metrics` 推迟 | NAS 负载低，数据不出境 |
| 镜像 | 只构建你的 NAS 对应的架构，推送到 GHCR；基础镜像固定到 digest；不挂载 docker.sock | 简单、安全 |
| 依赖更新 | 只开 Dependabot 的安全告警，关闭自动 PR；Claude 每月在 main 上跑一次 `npm outdated` 和 `npm audit` 后升级；CI 里跑 `npm audit --omit=dev` | 符合"只在 main 开发"的约定 |
| 角色一致性 | 默认文生图，加文本片段注入和种子锁定；不再把定妆照当 img2img 底图；等对方支持多参考图编辑后再开放参考层 | 现在的做法会带偏构图 |

### 4.6 部署拓扑与资源档位

```
            ┌─ 管理员与内测用户 ── VPN（Tailscale / 自建 Headscale / WireGuard）──┐
用户浏览器 ─┤                                                                    ▼
            └─（可选，D22）你选定的一条公网链路 ────────────▶ NAS Docker 网络 weave_net
                A. NAS 本机 Caddy（xcaddy 构建，带 DNS 插件）     weave:8787（只在内部网络）
                B. 已备案 VPS 上的 frps（SNI 透传，TLS 在 NAS 终结）卷：/data（SSD）/media（机械盘）
                C. 群晖 DSM 自带反向代理和证书                     /backups（另一块盘）
```

**容器加固**：

- 根文件系统只读；`/tmp` 用 tmpfs，并且 `size=64m`。
- `cap_drop: ALL`，开启 `no-new-privileges`。
- 日志用 json-file，单文件 10 MB，保留 5 个。
- `stop_grace_period` 设为 60s；HEALTHCHECK 改为检查 `/healthz`，`start_period` 设为 120s。

**资源档位**（PLT-26，用 `WEAVE_PROFILE` 切换）：

| 档位 | 适用 | 容器限制 | 行为 |
| --- | --- | --- | --- |
| standard（默认） | 内存 4 GB 及以上的 NAS | `mem_limit` 1g，`cpus` 2 | fast 和 heavy 两个通道各 1 个并发；heavy 运行时，fast 只处理图片；`FFMPEG_THREADS=2` |
| low | 内存 1–2 GB 的入门型号 | `mem_limit` 512m，`cpus` 1 | 关闭 heavy 通道（不做成片和代理视频转码）；`PROXY_MODE=off`；回填限速；scrypt 只允许 1 个并发 |

## 5. 功能蓝图（按领域）

**优先级**：

- **P0**：成熟站点的基本盘。
- **P1**：长期使用和成熟体验需要的功能。
- **P2**：增强功能，或者留给形态 B 和以后。

"里程碑"一列是计划交付的位置，MB 指形态 B 的待办。每个工作项都至少要有一条以它的编号开头的自动化测试，或者在附录 I 里列出的人工验收项（§6.0）。

### 5.1 账号与权限（ACC）

| 编号 | 功能点 | 优先级 | 里程碑 | 要点 |
| --- | --- | --- | --- | --- |

### 5.3 算子与凭证管理（OPR）：token 界面化

**TokenManager**：每个 login 型的算子实例各有一个。

1. 取 token 的规则：内存缓存命中、没被吊销、离到期还有 5 分钟以上，就直接用。否则走"单飞"登录，同一时刻只发一次 `POST /api/auth/login`。
2. 到期时间按以下顺序确定，界面上会标明用的是哪一种依据：JWT 里的 `exp` → 登录响应里的 `expires_in` 或 `expires_at` → 签发时间加上配置的有效期（默认 72 小时）。
3. 登录成功后把 token 加密写库。服务重启后直接恢复，不会重新登录。
4. 定时任务：每 10 分钟检查一次，剩余时间少于 12 小时就提前续期。每 30 分钟调用一次 `verify`；空闲 30 分钟后，第一次派发前也会先调用一次。
5. 业务请求遇到 401：作废 token，重新登录一次，并把请求重放一次。还是失败，就按凭证错误处理。
6. 登录失败：
   - 401 或 403：实例进入 `auth_error` 状态，熔断打开；之后按 5、10、20 分钟退避重试，最长间隔 30 分钟，避免把对方账号锁住；同时告警。期间用户的任务进入等待，不判为失败。
   - 5xx 或网络错误：归为"服务不可用"，交给熔断处理。

**测试连接清单**：新建、编辑和详情页都可以用，配置没保存也能测。前 3 步都通过才能直接保存，否则需要勾选"仍然保存"。每一次测试都写审计。

### 5.4 任务与调度（SCH）

**三个独立循环**：

- **派发器**：每 2 秒运行一次，任务有变化时立即运行。
- **轮询器**：按 `remote_jobs.next_poll_at` 驱动。
- **下载器**：固定并发 2 的工作池。

提交和下载都放进 Promise 池执行，节拍本身从不等待它们。所有状态迁移一律用 CAS 写法，例如 `UPDATE … WHERE id=? AND status='queued'`，影响行数为 0 就放弃本次操作。

**任务阶段**：

```
queued  ─ waiting_capacity / waiting_operator / backoff / waiting_user / waiting_confirm（提交结果不确定）
running ─ submitting → remote_queued → generating → postprocessing → downloading → finalizing
succeeded（partial=1 表示部分成功）/ failed（带 error_class）/ canceled（带 cancel_mode）/ paused
```

**错误分类决定处理方式**：

| 类型 | 典型来源 | 计入尝试次数 | 计入能力降级 | 处理方式 |
| --- | --- | --- | --- | --- |
| unavailable | 网络错误、5xx | 否 | 否（交给熔断） | 任务回到排队，状态为 waiting_operator |
| rate_limited | 429 | 否 | 否 | 按 `Retry-After` 暂停对该实例的派发 |
| auth | 重新登录后仍然 401 或 403 | 否 | 否 | 实例进入 auth_error，并告警 |
| invalid_input | 400、422 | 是 | 否 | 立即失败、不重试，给出可以照着改的提示 |
| content_blocked | 对方审核拦截 | 是 | 否 | 立即失败、不重试，提示"内容不合规" |
| remote_failed | 远端返回 failed | 是 | 是（需来自至少 2 个用户） | 退避后重试，优先换一台算子 |
| timeout | 超过硬超时 | 是 | 否 | 见下文"超时" |
| uncertain | 提交请求超时 | 否 | 否 | 任务进入 waiting_confirm，并提醒管理员。管理员可以"认领远端任务 id"或"确认重新提交"。系统**不自动**猜测并认领，等朋友支持 `client_task_id` 后再做自动处理 |
| not_found | 下载时返回 404 | 否 | 否 | 只重试下载，超过保留期才判为失败 |

**取消**：

| 情况 | 处理 |
| --- | --- |
| 还没提交 | 立即取消（`local`） |
| 算子支持取消 | 调用远端取消接口（`remote`） |
| 算子不支持取消（朋友那边目前就是这样） | 先弹窗确认："远端还会继续生成约 N 分钟，结果将丢弃"。确认后，任务标为 `abandoned`。远端作业继续以 120 秒的间隔轮询，并且**一直占用并发名额，直到远端结束** |

**超时**：

- **软超时**：取 p90×1.5 和配置值中较大的那个。到了只提醒用户"比平时慢"，任务继续跑。
- **硬超时**：
  - 远端还在 pending：继续等，不重复提交。
  - 远端在 running，且另有健康的算子：放弃这一次尝试，改派到别的算子。
  - 只有这一台算子：一直等到 `lateGraceSec`，默认 6 小时。
- **迟到的结果**：被放弃的作业后来完成了，而这个任务还没有通过其他尝试成功，就采用这个迟到的结果。

**派发：加权公平排队**

```
free[op][kind] = 实例上限 − 未结束的作业（含 abandoned）− 正在提交的数量
候选 = queued 且已到重试时间 且（用户开了自动调度 或 点了立即运行），最多取 500 条
按用户分组，组内按 manual_kick ↓、priority ↓、created_at ↑ 排序     ← 优先级只在用户自己的队列里生效
用户小顶堆，key = 近 24 小时 GPU 秒 ÷ 套餐权重；带 admin_boost 的任务最先出队
lane=idle（闲时通道）的任务，只有在同类没有 normal 候选、或处于闲时时段时才参与派发
循环：弹出 key 最小的用户 → 取该用户在"有空位的类型"里的第一个任务（且该用户在这个类型上的并发未达上限）
      → route() → CAS 抢占 → 异步提交 → 用户 key += 预计耗时 ÷ 权重 → 重新入堆
```

**路由 `route(t)`**：

1. 筛出候选算子：模型匹配、能力已启用、实例已启用且对该用户可见、没有在维护中，并且能通过参数校验。
2. 去掉熔断打开的和令牌不可用的。一个都不剩时，任务进入 waiting_operator。
3. 如果这个任务属于某个故事，优先选该故事上次成功的那台算子。
4. 重试时，排除上次远端失败的那台。
5. 在剩下的候选里取优先级最高的。最高优先级的算子只是满了、并没有故障时，任务继续等待，不溢出到低优先级的算子。

**轮询间隔**：

| 远端状态 | 间隔 |
| --- | --- |
| pending | 图片 4 秒，视频 20 秒 |
| running | 剩余预计时间的 10%，下限 12 秒 |
| postprocessing | 10 秒 |
| 超过软超时 | 30 秒 |
| 已放弃 | 120 秒 |
| 熔断打开 | 60 秒 |

每个实例默认限速 4 次请求/秒。

### 5.5 创作台（CRT）

**桌面布局**：结果流在左侧；底部是固定的 Composer；右侧是可以收起的灵感抽屉（360 px）。

```
[文生图 | 图生图 | 文生视频 | 图生视频]   模型：[织影·图像 ▾]   模板：电影海报 ×
```

**手机端**：

**提示词编译器 `shared/compose.ts`**：前后端共用，以服务端结果为准。

1. 正文：有模板时，先填变量，再追加补充描述。
2. 变量写法：正则为 `/\{([^{}\s]{1,16})\}/g`。取值顺序是用户填写 → 默认值 → 空串。`{{` 和 `}}` 转义为字面量。填完后清理连续出现的标点。
3. 同一互斥组（风格、光线、运镜等）只保留最后选中的那一个预设。
4. 拼接顺序：prefix 预设 → 正文 → suffix 预设（按构图、镜头、光线、色调、风格排序）。最后按短句去重。
5. 反向词：合并用户、模板、预设三处的反向词。如果算子不支持反向词，就把预设里的 `fallback_prompt` 转成正向约束追加进去，并给出警告。
6. 超长时，从末尾的修饰片段开始删，并给出警告。
7. 参数合并顺序：能力默认值 → 预设推荐值 → 模板参数 → 用户明确修改过的值。之后按尺寸表对齐，时长取最近的允许值，去掉算子不支持的字段。
8. 种子在服务端插入任务时生成。运镜作为一个可见的预设片段加入提示词。

### 5.6 预设、提示词库、热门效果与 AI 辅助（PRE）

**预设种类**：

- 风格、运镜（只用于视频）、速度、光线、色调：各自单选。
- 构图：景别、角度、构图三组，各组单选。
- 负向：可多选，每条带 `fallback_prompt`。

**热门与上新**：

- 邀请制的规模下，"热门"以运营精选为主。热门分只作参考：一个人一天之内用同一个模板，只计 1 次。

  ```
  score = Σ 0.5^(距今天数/7)（近 30 天的使用） + 2 × Σ 0.5^(距今天数/7)（近 30 天的收藏） + 精选加 3
  ```

### 5.7 工作流（WF）

工作流是织影产品层面的多步编排，**不是 ComfyUI 的节点图**。

- **定义方式**：用 TypeScript 写的步骤数组（附录 D）。生成步骤一律转成普通任务进入队列，因此能复用调度、重试、公平排队和计费。
- **"工作流"的另一层含义**：在后台上架 ComfyUI 侧的工作流模板。这需要朋友提供"模板 id + 参数"的通用执行接口，对应 OPR-15，由你决定先做哪一种（D23）。

| 步骤类型 | 作用 |
| --- | --- |
| generate | 生成图片或视频 |
| select | 人工挑选。无人值守时可以设为自动选第一张 |
| llm | 扩写、拆分镜头、生成动作建议 |
| local | 截取尾帧、无损拼接 |

**执行引擎**：

- 某一步的依赖全部完成后，才创建这一步的任务。
- 调度器发出完成、失败、取消等事件，引擎据此推进；另外每 30 秒保底扫描一次。
- 每个运行加锁，串行推进。
- 服务重启后，llm 和 local 步骤重新执行（这两类步骤是幂等的）。

**上限**：

- 每个用户最多 3 个活跃的运行。
- 每个运行最多派生 60 个任务。
- 单步 forEach 最多 24 项。

### 5.12 平台工程与安全（PLT）

**请求处理链**：requestId → `trustProxy` 解析真实 IP → 维护模式 → 安全头 → 非 GET 请求做 Origin 校验 → 会话 → 限流 → 角色校验和重新验证 → 处理 → 访问日志（提示词不写进访问日志）和审计 → 统一的错误体 `{error: 中文, requestId}`。

**CSP**：

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; media-src 'self' blob:; connect-src 'self';
object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```

`/api/files` 另外加上 `sandbox` 和 `Cross-Origin-Resource-Policy: same-origin`，并且不提供任何 SVG。

**内容类型白名单与例外**：默认只接受 `application/json`。例外只有两类：

- 上传路由，接受 `multipart/form-data`。
- `/api/client-errors`，接受 `text/plain`。

例外路由同样要做 Origin 校验。

**上传校验**（PLT-12）：

| 类型 | 流程 |
| --- | --- |
| 图片（png、jpeg、webp、gif） | 1. 流式写入 `/media/.tmp`，超过上限立即中止。2. 用纯 JS 读文件头，确认真实格式；任一边大于 8192，或总像素超过 4000 万，直接拒绝。3. 用纯 JS 去掉元数据：JPEG 删除 APP1 和 APP13 段，PNG 删除 eXIf、tEXt、iTXt 块。**不重新编码**。4. 计算 sha256，检查配额，原子 rename |
| 视频、音频 | 1. 先放进隔离区。2. 用 ffprobe 校验容器和编码是否在白名单内（mp4/mov/webm；H.264/H.265/VP9/AV1；aac/mp3/opus/wav），时长和码率是否超限。3. 用 `-map_metadata -1 -c copy` 重新封装，清掉元数据。4. 移入正式目录 |
| 用人像做图生图或图生视频 | 需要勾选"已取得本人同意"，并写入记录 |

**出站请求 safeFetch**：

- 只允许 http 和 https。
- 用 `net.BlockList` 拦截环回、私网、链路本地、CGNAT 和云元数据地址。算子配置里可以显式勾选"允许内网地址"。
- 把连接钉在已经校验过的 IP 上，防止 DNS 重绑定。
- 重定向手动处理，每一跳都重新校验，最多 3 跳。
- 限制响应体大小和总超时。

### 5.13 合规（CMP）

> 本节只列确定的要点。凡是标"需确认"的，都必须在形态 A-公网或形态 B 立项之前，由法务或主管部门确认。所有合规能力都做成"可配置、可开关"，避免返工。

| 法规或标准 | 对织影意味着什么 |
| --- | --- |
| ICP 备案、公安联网备案 | 在境内的服务器上面向公众提供网站服务，需要备案。家庭宽带通常办不了备案。个人主体能不能承载这类服务，**需确认** |
| 《网络安全法》 | 网络日志留存不少于六个月；要有安全事件的应急处置能力。等级保护（等保）如何定级、是否需要备案，**需确认**（形态 B） |
| 《个人信息保护法》 | 用隐私政策告知用户并取得同意。要披露把个人信息提供给第三方的情况（朋友的算子、审核服务、短信服务）。用户有查阅、删除、注销的权利。人脸属于敏感个人信息，需要单独同意。是否需要做个人信息保护影响评估、是否涉及数据出境，**需确认** |
| 《生成式人工智能服务管理暂行办法》 | 面向境内公众提供服务时，涉及内容安全、标识、投诉举报、防止未成年人过度依赖。发现违法内容时，需要采取处置措施、保存记录，并向主管部门报告（具体义务**需对照原文**）。"未向境内公众提供服务"是否适用于形态 A，**需确认** |
| 深度合成相关规定 | 显著标识；真实身份认证；提供人脸编辑功能时，要提示使用者取得被编辑者的单独同意。算法备案，以及具有舆论属性时的安全评估，**需确认** |
| 大模型登记或备案 | 织影的算子是朋友自己部署的模型，应该走哪条路径，**需向属地网信办确认**。另外，各个模型的许可证是否允许对外提供服务和商用，**需确认** |
| 《人工智能生成合成内容标识办法》与 GB 45438-2025（均自 2025-09-01 起施行） | 显式标识（图片上的文字、视频起始画面的提示）和隐式标识（文件元数据里写入生成标签、服务提供者、内容编号等）。具体的字段写法和量化参数**需对照原文**。开设广场或分享链接之后，作为传播平台还要承担检测和提示义务 |
| 协议与权利 | 写明生成内容的权利归属和使用许可、用户对上传素材的版权责任、提示词和参考图会传到算子方并在那里留存。由 Claude 起草，**需你审定，最好再请懂法律的人看一遍** |

## 6. 分阶段路线图与验收

### 6.0 推进规则

**每个工作项的完成标准**：

1. `npm run verify` 全部通过。工作项至少要有一条测试名以它的编号开头（例如 `test('OPR-04 401 时只重登一次', …)`）。`scripts/trace.ts` 会检查本文档里所有已排期的编号；MB 和"以后"的除外。只能人工验收的工作项，必须列在附录 I.3 里。
2. 用旧数据库升级后，服务能正常启动，旧数据完整。
3. Playwright 在 375 px 和 1440 px 两个宽度下截图，页面不出现横向滚动。
4. 不新增渐变，只使用一个强调色。
5. README 和 CHANGELOG 同步更新。
6. 直接推送到 main。还没做完的功能用功能开关关闭（M1 之前用环境变量，之后用 `app_settings`），保证 main 随时可以部署。

**每个里程碑结束时**：

- 打一个 `v0.x.0` 的 tag，写好发布说明。
- 你在 NAS 上运行 `selfcheck`，把报告贴回来（§7.3）。
- 统计代码量，对照预算检查。
- 从 M2 起，每个里程碑的预算里都预留 1 个会话，用来修复内测反馈。

**验收的执行人**（每条验收标准前都会标明）：

| 标记 | 含义 | 谁来做 |
| --- | --- | --- |
| **[CI]** | 在 GitHub Actions 或 Claude 的沙箱里自动验证，使用假算子 | Claude |
| **[NAS]** | 在你的 NAS 上运行 `docker exec weave node scripts/selfcheck.ts <参数>`，把输出的报告贴回来 | 你（每次 5–30 分钟） |
| **[真机]** | 在你的手机或电脑浏览器上手动操作，按清单逐项勾选 | 你（每次不超过 10 分钟） |

Claude 的开发沙箱连不上朋友的算子（已实测），也接触不到你的 NAS 和真机。所以凡是涉及真实算子、真实硬件或真实网络链路的验收，都是 [NAS] 或 [真机]。

**测量方法**（详见附录 I）：

- 前端流畅度：Playwright + CDP，CPU 降速 4 倍，用 `PerformanceObserver('longtask')` 统计，要求"没有超过 50 ms 的长任务"。不用"60 fps""输入延迟"这类主观指标。
- 后端性能：在 `docker run --cpus=2 --memory=1g` 下用 `scripts/bench.ts` 测量；低配档位改用 `--cpus=1 --memory=512m`。
- 和具体硬件挂钩的指标（例如"缩略图 3 秒内生成"），以你 NAS 上的 `selfcheck --perf` 实测结果为准。

**顺序原则**：先止血，再打地基，然后做安全基线并开放内测，接着做可靠性和上线，最后加功能。在这个过程中，你点名要的功能尽早交付一个可用版本。M5 到 M8 之间可以根据你的反馈调整顺序，依赖关系见 §6.17。

## 8. 风险、取舍、未采纳的意见与暂不做事项

### 8.1 主要风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 一张 GPU 撑不起长篇故事 | 一个 60 镜头的故事需要 17–33 GPU 小时；8–16 个活跃用户就能把整张卡占满 | 两段式生产；闲时通道；公平调度；全站容量护栏；根本办法是接入更多算子（M3 起支持） |
| **模型来源与性质未确认** | 如果视频其实是在调用 MiniMax 云端：数据会流向第三方，每次都有费用，容量测算全部失效。对方接口文档已写明文生视频使用 Uncensored（去审查）编码器，合规风险显著上升 | §9.2 第 13 项必须在 M0a 期间问清楚；确认之前，§2.5 和附录 B 都只是假设；形态 A 至少要有输入审核和红线拦截，并在协议里写明用户的责任 |
| NAS 到算子之间走公网明文 HTTP | appid、secret、token 和用户的内容都可能被窃听 | 只能由朋友那边加上 HTTPS，或者双方组 WireGuard 或 Tailscale。完成之前，后台一直显示红色警告，上线就绪自检也不通过 |
| 数据在第三方服务器上留存 | 提示词和参考图留在朋友的服务器上，织影删不掉 | 在隐私政策里如实披露；和朋友签合作约定，约定留存期限（§7.1 第 23 项） |
| 依赖朋友的单台机器 | 那台机器停机，全站就没法生成 | 熔断，不计入失败；任务排队等待；维护模式显示预计恢复时间；接入第二台算子 |
| 算子的接口语义还没确认 | 复现、变体等能力可能打折扣 | 所有相关能力都由能力声明控制，确认之前保守地关闭；用假算子和 `selfcheck` 联调 |
| Claude 接触不到真实算子和设备 | 有些验收无法自动完成 | 所有验收标准都标明执行人；用 `selfcheck` 一键生成报告；每个里程碑你需要投入的时间见 §7.3 |
| 内测阶段可能只有 HTTP | Secure cookie、`crypto.subtle`、Web Locks、浏览器通知都会受影响 | HTTP 模式下自动降级（换 cookie 名、不做 PoW、先检测 API 是否可用）；用 Tailscale 时建议开 `tailscale cert` |
| 在大陆用 Tailscale 不稳定 | 内测朋友可能连不上 | 提供自建 Headscale + DERP 和 WireGuard 两种备选方案，附排错指引 |
| 家用 NAS 做公开服务有先天限制 | 办不了备案、可能违反运营商协议、上行带宽小、停电断网 | 形态 A 默认只走 VPN；形态 B 是否把边缘放到云上由 D25 决定 |
| NAS 的 CPU 和内存弱 | 转码和成片慢；ffmpeg 子进程的内存计入容器限额，可能导致 OOM | 提供 standard 和 low 两个资源档位；heavy 通道单并发；上传的图片不重新编码；默认用复制模式拼接；临时文件不放在 tmpfs 里 |
| `node:sqlite` 仍是实验特性，而且是同步 API | 慢查询会阻塞整个进程；升级 Node 时 API 可能变化 | 所有列表都走索引和分页；CI 里有查询性能回归测试；固定 Node 的次版本；大数据量的处理放进可限速的 jobs |
| 范围大 | 迟迟看不到成果，代码越写越难维护 | 总量压缩到 159–196 会话；设代码量预算；你点名的功能先交付可用版本；每个里程碑都能单独验收 |
| 只在 main 开发、直接推送 | 没有代码评审这道闸门 | 本地 verify、pre-push 钩子、推送后跑 CI、功能开关；生产环境只部署打过 tag 的版本 |
| 故事拆表是单向的大迁移 | 迁移失败可能丢数据 | 迁移前备份；按需迁移，每个故事单独一个事务，迁移后回读校验；永久保留原始 JSON 快照；失败的故事以只读方式打开 |
| 回滚可能丢数据 | 不兼容迁移之后回滚，会丢失升级后产生的数据 | 尽量把迁移设计成兼容的；回滚脚本会明确提示丢失的时间窗口；先备份再更新 |
| 法规理解有不确定性 | 可能返工，也可能违规 | 所有"需确认"的事项，在 A-公网或 B 立项前由法务确认；合规能力都做成可配置、可开关 |
| 主密钥和数据库放在同一个目录 | 备份泄露后，密钥可以被解开 | 强烈建议把主密钥放在环境变量里；否则后台持续警告 |

### 8.2 关键取舍

| 取舍 | 选择 | 代价 |
| --- | --- | --- |
| 晚提交，还是充分利用对方的队列 | 每个实例的在跑上限设得小（视频 1、图片 2），任务尽量留在织影自己的队列里 | 损失一部分连续吞吐；换来取消、公平和计数都可控 |
| 被放弃的作业是否占用名额 | 计入并发，直到远端真正结束 | 取消之后的一段时间里看起来"没有空位"，界面上会解释原因 |
| 硬超时后是否重新提交 | 远端 pending 时继续等；running 时改派到别的算子；只有一台时等到 6 小时 | 极端情况下要等很久，但同一个镜头不会占用双份 GPU |
| 提交超时怎么处理 | 进入"待确认"，由管理员处理；不自动猜测、认领远端任务 | 需要人工介入；等朋友支持 `client_task_id` 后改为自动处理 |
| ETA 怎么算 | 简单公式，不模拟整套派发 | 多算子、多用户交错时误差会大一些 |
| 字段级"后写者胜"，还是 CRDT | 字段级后写者胜 | 不支持多人实时协作；对"一个人多台设备"的场景足够 |
| 工作流怎么定义 | 在代码里定义，加一个通用执行引擎 | 运营人员不能在后台新建工作流；新工作流要等 Claude 来写 |
| 积分账本 | 单一余额加流水 | 没有"积分过期"；收费时（MB）需要再做一轮 |
| 上传的图片 | 不重新编码，只剥离元数据 | 不能顺带压缩体积 |
| 搜索 | FTS5 trigram，`detail=none` | 没有相关性排序和摘要片段；结果按时间排序 |
| 访问链路 | 只实现你选定的一条 | 换链路时需要再开发 1–2 个会话 |
| 自己做可观测性 | 只做错误聚合、告警和简单采样 | 不如 Sentry 或 Grafana 强大；换来数据不出境、NAS 负载低 |
| 权限点写在代码里 | 只有三种固定角色 | 不能在后台自定义角色 |
| 后台分包 | 任何人都能下载，接口对非管理员返回 404 | 后台的路由名和接口名可以被看到，但看不到任何数据 |

## 9. 给算子提供方（朋友）的接口建议

下面的内容会在 M3 整理成 `docs/FRIEND_API_WISHLIST.md`，由你转给朋友。其中 §9.2 第 1–4 项和第 13 项请现在就问。

### 9.1 改进清单

**P0：直接影响可靠性、安全和算力浪费**

1. **取消接口** `POST /api/tasks/{id}/cancel`。pending 的任务从 ComfyUI 队列里删除；running 的调用 `/interrupt`。返回 `canceled` 或 `too_late`。
2. **进度和排队信息**：任务详情里加上 `progress`（0–1）、`queue_position`、`eta_seconds`。
3. **全局队列状态** `GET /api/queue`：返回 `{pending, running, avg_seconds_by_type}`。
4. **种子语义**：传 `seed=-1` 或不传，表示随机；结果里**回传实际用的种子**。
5. **产物文件**：说明文件保留多久；下载支持 `Range` 并返回 `Content-Length`，最好再给出 `sha256`；结果里带上视频的时长、帧率、宽高、编码和音轨信息。
6. **规范的错误码**：参数错误返回 4xx 并附带 `code`；队列满时返回 429 和 `Retry-After`；用 `OOM`、`WORKFLOW_ERROR`、`CONTENT_BLOCKED` 区分失败原因。
7. **加密链路**：接口加 HTTPS，或者和 NAS 组 WireGuard 或 Tailscale；至少要设 IP 白名单。

**P1：体验与效率**

8. **幂等提交**：支持 `client_task_id` 或 `Idempotency-Key`。有了它，织影才能在网络超时后安全地自动对账。
9. **能力发现** `GET /api/capabilities`：返回模型和版本、参数范围、对齐倍数、时长范围、典型耗时。
10. **超分开关** `upscale: bool`，或者额外输出一份低码率的预览版。这样可以"草稿不超分、定稿再超分"，草稿大约快一倍。
11. **补齐参数**：图生视频支持 `last_frame`；图生图支持 `denoise`、`cfg` 和多张参考图；视频支持负向提示词。最好再提供一个**多参考图编辑**接口，它决定了角色一致性能做到什么程度。
12. **原生批量**：文生图支持 `batch_size`。
13. **短任务插队**：支持 `priority` 或 `front`（ComfyUI 的 `/prompt` 本身就支持 `front`）。
14. **批量查询** `GET /api/tasks?ids=…` 和 `?since=`。
15. **通用工作流执行接口**：提交"模板 id + 参数"，新效果就能直接在织影后台上架，双方都不用改代码。对应 OPR-15 和 D23（**从 P2 上调为 P1**）。

**P2**

16. 令牌：登录响应里带 `expires_at`；说明多个 token 能否同时有效；提供吊销接口。
17. `/health` 返回显存、队列长度、`maintenance` 标志和预计恢复时间。
18. 输入文件复用：先上传一次拿到 `file_id`，之后多次引用。
19. 视频结果附带一张封面帧。
20. 图片超分接口。
21. 给织影单独分配一个生产环境的 appid，和开发、测试分开。
22. 以后可以考虑的新算子：TTS 配音、口型同步、配乐和音效、补帧、抠图和局部重绘、视觉 LLM。

### 9.2 需要朋友尽快确认的问题

| # | 问题 | 影响 | 最晚于 |
| --- | --- | --- | --- |
| 1 | `/health` 接口存在吗？（**最急**：如果不存在，现在的代码会一直判定服务不可用） | 健康检查 | M0a |
| 2 | `seed=0` 表示随机还是固定？能不能回传实际使用的种子？ | 复现与变体 | M0a |
| 3 | token 是 JWT 吗？有效期是不是固定 72 小时？重新登录会不会让旧 token 失效？能否分配开发和生产两个 appid？ | 令牌管理 | M1 |
| 4 | `GET /api/tasks` 返回的是本 appid 的任务，还是所有人的？字段和单条查询一致吗？`/api/products` 是否只返回本 appid 的产物？ | 批量轮询、隐私 | M1 |
| 5 | 每个 appid 有没有并发数、提交数或请求频率的限制？ | 实例限额 | M3 |
| 6 | 产物在对方服务器上保留多久？下载支持 Range 吗？ | 下载重试的时间窗口、断点续传 | M3 |
| 7 | 图生图是"按指令编辑"还是"按强度重绘"？有没有 strength 参数？能不能传多张参考图？ | 变体、风格转绘、角色一致性 | M5a |

### A.1 适配器接口 v2（`server/operators/types.ts`，节选）

只用可擦除的 TS 语法：不用参数属性，也不用 enum。这样能直接在 Node 原生的类型剥离模式下运行。

```ts
export interface OperatorAdapter<C = Json> {
  type: string;                 // 'comfyweb' | 'weave-http' | 'openai-llm' | 'openai-tts' | 'mock'
  label: string;                // 「ComfyUI Web API（appid 登录）」
  configSchema: FieldSpec[];    // 后台表单据此生成；secret:true 的字段存入 secrets 表，只写不读
  auth: 'none' | 'static' | 'login';
  create(ctx: OperatorContext<C>): OperatorClient; // ctx: baseUrl / config / secrets / getToken() / safeFetch / log
}

export interface OperatorClient {
  probe(): Promise<{ ok: boolean; latencyMs: number; detail?: string }>;
  login?(): Promise<TokenInfo>;
  verify?(token: string): Promise<{ valid: boolean; identity?: Json }>;
  capabilities(): Promise<CapabilitySpec[]>;
  submit(job: SubmitInput): Promise<{ remoteIds: string[]; seeds: number[] }>;
  poll(remoteId: string): Promise<RemoteStatus>;                         // 只查状态
  pollMany?(ids: string[]): Promise<Map<string, RemoteStatus>>;
  openDownload(ref: OutputRef, range?: { start: number }): Promise<Response>; // 返回流，由下载器落盘
  cancel?(remoteId: string): Promise<'canceled' | 'too_late' | 'unsupported'>;
  listRemote?(cursor?: string): Promise<RemoteJobSummary[]>;
  listTemplates?(): Promise<RemoteTemplate[]>;                           // OPR-15，算子侧工作流模板
  chat?(messages: ChatMessage[], opts: ChatOptions): Promise<{ content: string; usage?: Usage }>;
  speech?(input: SpeechInput): Promise<Response>;                        // OPR-14，TTS
}

export type OperatorErrorClass =
  | 'unavailable' | 'auth' | 'rate_limited' | 'invalid_input' | 'content_blocked'
  | 'remote_failed' | 'timeout' | 'not_found' | 'uncertain' | 'internal';

export class OperatorError extends Error {
  readonly cls: OperatorErrorClass;
  readonly userMessage: string;     // 脱敏后给用户看
  readonly detail?: string;         // 原始信息，只给管理员看
  readonly retryAfterMs?: number;
  readonly infra: boolean;          // 是否计入能力级降级（只有基础设施类错误才计入）
  constructor(cls: OperatorErrorClass, userMessage: string,
              opts: { detail?: string; retryAfterMs?: number; infra?: boolean } = {}) {
    super(opts.detail ?? userMessage);
    this.cls = cls;
    this.userMessage = userMessage;
    this.detail = opts.detail;
    this.retryAfterMs = opts.retryAfterMs;
    this.infra = opts.infra ?? (cls === 'remote_failed' || cls === 'internal');
  }
}
```

## 附录 B · 积分与计费规则（M9，精简版）

**积分的定义**：

- 价格以模型目录里的 `pricing` 为准。
- 对 5090 这类按 GPU 时长计算的模型，默认定价参照"1 积分 ≈ 10 GPU 秒"。这个比例只用来在仪表盘上换算容量：每天约 8,640 积分。
- 形态 A 下，积分是**非货币配额**（D24）。

**默认定价**（后台可改，带试算器）：

| 类型 | 公式 | 默认值 | 示例 |
| --- | --- | --- | --- |
| 文生图 | ⌈单价 × 张数 × 档位倍率⌉ | 单价 4；≤1.2 MP 倍率为 1，≤2.6 MP 倍率为 2 | 标准 4 张 = 16；高清 4 张 = 32 |
| 图生图 | 同上 | 单价 5 | 高清 1 张 = 10 |
| 视频 | ⌈(base + 每秒价 × 秒数) × 档位倍率⌉ | base 40，每秒 12 | 5 秒 = 100；8 秒 = 136；15 秒 = 220 |
| AI 助手 | 按次 | 润色 0；大纲、章节 2；其余 1 | — |
| TTS | 按字数 | 每 100 字 1 | — |

**默认套餐**（需要你确认，D16）：

| 套餐 | 每日免费 | 每月积分 | 排队上限 | 同时运行 | 调度权重 | 存储 | 功能 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 免费 free | 40 | 0（注册赠送 300） | 30 | 1 | 1 | 5 GB | 视频最长 10 秒 |
| 创作者 creator | 80 | 6,000 | 300 | 2 | 2 | 100 GB | 视频最长 15 秒 |
| 工作室 studio | 120 | 20,000 | 1,000 | 2 | 3 | 500 GB | 全部功能 |

> **说明（有意为之）**：免费用户每天的 40 积分只够出图（10 张标准图），出不了视频（一条 5 秒视频要 100 积分）。视频只能用注册赠送的 300 积分（约 3 条）或兑换码来出。原因是一张 5090 每天只能出 48–96 条视频，如果每个免费用户每天都能出视频，几十个人就会把容量占满。

**扣减与账本**（单一余额）：

- 先扣今日免费额度：`daily_usage` 记录每个用户每天的用量，每天 0 点（Asia/Shanghai）重置。不够时再扣 `users.credit_balance`。
- 每一次余额变动都在一个 `BEGIN IMMEDIATE` 事务里完成，同时写一条只追加的 `credit_ledger` 流水。

**任务生命周期与积分动作**：

| 事件 | 积分动作 |
| --- | --- |
| 创建任务（单个或批量；批量要么全部成功，要么全部失败） | 冻结（`credit_holds`）。余额不足时返回 402，提示"需要 30 积分，当前 12" |
| 服务不可用时等待、自动重试 | 不变（冻结按任务计，不按尝试次数计） |
| 成功 | 结算；部分成功时按实际产出的比例结算，剩下的退还 |
| 最终失败、超时、排队中被取消、删除任务或故事、管理员强制取消 | 全额退还 |
| 运行中被取消（远端停不下来） | 按 `cancelRunningRefundRate` 退还（默认 1.0）；GPU 时长照样计入公平调度 |
| 手动重试已失败的任务 | 重新冻结；管理员勾选"免费重试"时不冻结 |
| 用户被封禁 | 取消该用户所有排队中的任务，并退还积分 |
| 老任务（没有 `hold_id`） | 跳过 |

**对账**：每天凌晨核对每个用户的 `credit_balance` 是否等于流水之和。冻结超过 48 小时、而对应任务已经结束的，自动补做结算或退还。发现不一致就写审计，并通知超管。

**积分上线之前（M2–M8）**：用每日上限代替积分（SCH-03）。

**推迟到 MB 再做**：积分批次和过期机制、按原批次退还、套餐顺延、在线支付。

## 附录 D · 官方工作流定义（代码定义，M8a）

工作流就是 `server/workflows/defs/*.ts` 里的一个普通对象。执行引擎解释其中 `generate`、`select`、`llm`、`local` 四种步骤。步骤之间用 TypeScript 函数取值，不用字符串表达式，所以不需要表达式引擎，也不存在注入风险。

### D.1 W1 四选一出视频

预计耗时：4 张图约 4–8 分钟，再加 1 段视频约 20–30 分钟。

```ts
export const w1: WorkflowDef = {
  id: 'w1-pick-to-video', title: '四选一出视频',
  inputs: [
    { key: 'idea', label: '画面描述', type: 'text', multiline: true, required: true, placeholder: '雨夜霓虹街头，撑伞的少女回眸' },
    { key: 'style', label: '风格', type: 'preset', presetKind: 'style', default: 'style.cinematic' },
    { key: 'motion', label: '动作与运镜', type: 'text', default: '人物缓缓转身看向镜头，镜头缓慢推进' },
    { key: 'duration', label: '视频时长', type: 'select', default: 5, options: [5, 8, 10] },
  ],
  steps: [
    { id: 'kf', kind: 'generate', label: '生成 4 张候选',
      task: (c) => ({ type: 't2i', prompt: c.inputs.idea, presets: [c.inputs.style, 'neg.quality'],
                      params: { aspectRatio: '16:9', tier: 'standard', count: 4 } }) },
    { id: 'pick', kind: 'select', label: '挑一张做首帧', from: 'kf', min: 1, max: 1, auto: 'first',
      hint: '选构图和人物最满意的一张，视频会从这张开始动' },
    { id: 'vid', kind: 'generate', label: '图生视频',
      task: (c) => ({ type: 'i2v', prompt: c.inputs.motion, presets: [c.inputs.style, 'neg.video'],
                      inputs: { firstFrame: c.steps.pick.assets[0] },
                      params: { aspectRatio: '16:9', duration: c.inputs.duration } }) },
  ],
  outputs: ['vid'],
};
```

### D.2 W4 长镜头接力

```ts
export const w4: WorkflowDef = {
  id: 'w4-relay', title: '长镜头接力',
  inputs: [
    { key: 'start', label: '起始画面', type: 'image', required: true },
    { key: 'beats', label: '分段动作（每行一段，2–4 段）', type: 'lines', min: 2, max: 4,
      default: ['少女推开木门走进花园', '她弯腰拾起地上的信封', '她抬头望向远处的钟楼，镜头缓缓升起'] },
    { key: 'duration', label: '每段时长', type: 'select', default: 8, options: [5, 8, 10] },
  ],
  steps: [
    { id: 'seg', kind: 'generate', label: '逐段生成', forEach: { over: (c) => c.inputs.beats, mode: 'sequential' },
      task: (c, item, i, prev) => ({ type: 'i2v', prompt: item, presets: ['neg.video'],
        inputs: { firstFrame: i === 0 ? c.inputs.start : { lastFrameOf: prev.assets[0] } },
        params: { duration: c.inputs.duration } }) },
    { id: 'join', kind: 'local', label: '拼接成片', op: 'concat_videos', source: (c) => c.steps.seg.assets },
  ],
  outputs: ['join', 'seg'],
};
```

`{ lastFrameOf }` 的意思是：由引擎从上一段视频里截取尾帧，并把它作为一个新素材入库，血缘记为 `frame`。

| 编号 | 名称 | 步骤 | 优先级 |
| --- | --- | --- | --- |
| W2 | 角色定妆照 | 文生图 3:4 出 4 张（半身、纯色背景、正面）→ 挑 1 张 → 可选：写回故事角色的主参考图 | P0（M8a） |

### E.2 增量操作 ops

接口：`POST /api/stories/:id/ops`，请求体为 `{baseRev, clientId, ops[]}`。

```ts
type StoryOp =
  | { op: 'create'; entity: Entity; id: string; parentId?: string; value: Record<string, unknown> }
  | { op: 'set';    entity: Entity; id: string; patch: Record<string, unknown> }   // 字段级，后写者胜
  | { op: 'move';   entity: Entity; id: string; parentId?: string; sortKey: string } // 分数排序键，只改一行
  | { op: 'delete'; entity: Entity; id: string }                                     // 级联删除子节点，删除优先
  | { op: 'link';   shotId: string; elementId: string; on: boolean }
  | { op: 'ref';    entityType: string; entityId: string; assetId: string; role: string; on: boolean };
```

服务端处理步骤：

1. `BEGIN IMMEDIATE`，校验归属。
2. 每条 op 先过 Zod 白名单，再执行。指向已删除实体的 op 放进返回结果的 `ignored` 里。
3. `rev` 加 1，写一条 `story_revisions`。
4. 结构有变化时，重新计算 `stats`。
5. 按需生成快照。
6. COMMIT，然后发出 SSE 事件 `story-rev`。

旧版前端发来的 `PUT /api/stories/:id` 一律返回 409，提示"织影已升级，请刷新页面"。

### E.3 迁移步骤（按需迁移，加后台逐个迁移，每个故事一个事务）

1. **触发时机**：用户打开一个 `schema=1` 的故事时立即迁移这一个；其余的故事由 `jobs` 在后台逐个迁移，可以限速。
2. **解析 `stories.data`**：
   - logline、genre、tone、visualStyle、aspectRatio 写入 `settings`；outline 写入 `story_docs`。
   - characters 写入 `story_elements`，**保留原 id**；`appearance` 改名为 `snippet`；`referenceAssetId` 写入 `entity_assets` 的 primary 角色。
   - 场次地点里不重复的字符串，各建一个 location 设定。
   - 章、场、镜、台词**全部保留原 id**，所以 `assets.shot_id` 和 `tasks.shot_id` 都不用改。
   - `characterIds` 写入 `shot_elements`。**以 `char_` 开头的伪 shotId 只在这一步转换为 `element_id`**，别处不再重复处理。
3. **回读校验**：把新结构还原成旧 JSON，比对章、场、镜、台词、角色的数量和 id 集合。不一致就回滚这个故事，保持 `schema=1`，并以只读方式打开。
4. **成功后**：设 `schema=2`、`rev=1`；写一份 `migration` 快照，内容是**原始 JSON**，永久保留；重算 `stats` 和封面。
5. **全部迁完之后**：把 `data` 列改名为 `legacy_data`，保留一个大版本后再删除。删除这一步是不兼容迁移，会提高 `min_code_version`。

### E.4 有效选定

```sql
SELECT shot_id, purpose, id FROM (
  SELECT shot_id, purpose, id, ROW_NUMBER() OVER (PARTITION BY shot_id, purpose ORDER BY seq DESC) rn
  FROM assets WHERE story_id = ? AND shot_id IS NOT NULL AND deleted_at IS NULL AND COALESCE(flag,'') <> 'reject'
) WHERE rn = 1;   -- 再和 story_shots 里的显式固定合并（显式固定优先），就得到 /media/selected
```

### I.2 `selfcheck` 自检脚本（PLT-27）

| 参数 | 检查内容 | 首次提供于 |
